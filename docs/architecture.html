Integration Layer Design: 3D Sales Workspace

Backend Assessment, Part A (architecture and design) · Candidate: Rohit Sharma · 20 October 2026

1. Architecture flow

1.1 Trust zones

ZoneContainsTrust
Untrusted zoneBrowser (React workspace with the 3D room and sidebar)Untrusted. Every request is authenticated and authorised on the server.
Customer identityOpenID Connect identity providerIssues and signs tokens; the API verifies them against its JWKS.
Customer Azure tenantFirewall (WAF), Integration API, Redis, PostgreSQL, workers, adapters, Blob storage, Key Vault, monitoringTrusted. Our code and data stores.
Enterprise systemsSizing tool, Pricing ERP, Catalogue, Document vault, Host project APIOwned by other teams and cannot be changed. Their responses are validated as untrusted input.

1.2 Read flow: selecting an item fills the sidebar

  1. The user signs in through the identity provider (OIDC authorisation code with PKCE) and the browser receives an access token.
  2. The browser calls the Integration API over HTTPS through the customer WAF, sending the token as a Bearer header.
  3. The API verifies the token (signature against JWKS, issuer, audience, expiry) and builds the caller context: role, country and customer group.
  4. The API loads the item from PostgreSQL and fans out to the adapters in parallel. Adapters run in-process, one per system.
  5. Each adapter checks the Redis cache first. On a miss it takes a token from the global rate limit in Redis and calls its system over HTTPS REST.
  6. Pricing is called only if the caller is entitled to see prices. The entitlement check runs before the cache is read.
  7. Every vendor response is validated against a schema. The API returns one section per system, each with its own status, so one failing system never blanks the sidebar.

1.3 Write flow: re-sizing an item

  1. The browser sends the re-size request with an idempotency key, so a retried click cannot apply twice.
  2. The API calls the sizing tool through its adapter, with the user's delegated (OBO) token.
  3. If the recommended variant changed, one PostgreSQL transaction updates the item's variant and 3D model reference, its BOM line and its version, and writes an outbox row.
  4. A worker reads the outbox and saves the change to the Host project API with If-Match on the version, so a save is never duplicated and never overwrites a newer change.

1.4 Background and slow work

  • Job queue in Redis. Slow calls and retries become jobs. The job ID is built from type, item, version and change, so duplicate requests merge into one job.
  • Slow-service worker. Runs queued calls to slow or rate-limited systems through the same adapters.
  • Scheduled worker. Imports the catalogue nightly export and change feed into PostgreSQL with an upsert by revision, so an old update never overwrites a newer one. It stores 3D models in Blob storage.
  • Dead-letter queue. Jobs that keep failing go to the DLQ for inspection and alerting.

1.5 Inbound events from the host

The Host project API sends a webhook over HTTPS when a project changes elsewhere. It passes the WAF, its HMAC signature is verified, and its event ID is checked so a repeated event is processed only once.

1.6 Direct downloads

  • 3D models: the browser downloads glTF files from Blob storage with a SAS signed URL.
  • Documents: the browser downloads a file directly from the Document vault with a short-lived signed URL.

Large files never pass through the Integration API.

1.8 Supporting services

  • Key Vault: holds vendor credentials and the webhook key; no secrets in code.
  • Monitoring: collects logs, metrics and traces from all services.

1.9 AI assistant flow

The assistant runs in its own container inside the tenant and never calls an enterprise system directly. Every tool it uses is a call to the same Integration API services the sidebar uses, made with the user's own context, so it can never see more than the user can.

  1. Question in. The browser sends the question to the Integration API (HTTPS, Bearer JWT). The API verifies the token and forwards the question with the caller context to the Assistant container over internal HTTPS.
  2. Orchestrator. Picks the module agent that fits the question (BOM, sizing or catalogue) and loads the conversation memory from PostgreSQL.
  3. Module agent. Reasons with the Private LLM over a private endpoint. The LLM has no credentials and no outbound internet, so it can only suggest tool calls, never perform them.
  4. Read or write? A read tool (for example get_item_details, get_bom_cost) runs straight away. A write tool (for example resize_item) goes to human in the loop: the user sees the proposed change and must confirm it. On confirm, the UI receives a signed, single-use confirmation bound to the user, item and arguments. The model cannot produce this confirmation itself. On decline, the agent is told no and nothing changes.
  5. Tool registry (MCP). Tool calls carry only IDs and parameters. They run as the user, against the Integration API services, through the same entitlements, cache, adapters and rate limits as the sidebar.
  6. Validator / formatter. Checks the draft answer before it leaves: no price if the user may not see prices, plain text only, and every figure must come from a tool result. If a check fails, the answer goes back to the agent with a critique.
  7. Answer out. The answer is returned to the Integration API and streamed to the browser over SSE. The question, every tool call, entitlement decisions, confirmations and the answer are written to the audit log in PostgreSQL.

Prompt injection. Catalogue text and document content are untrusted. They reach the model only as clearly separated data, never as instructions. Even if injected text convinces the model, it still cannot exceed the user's permissions, cannot write without the user's confirmation, and has no network path to send data out.

1.10 Example: re-sizing a drive through the assistant

A sales engineer in Germany asks the assistant: "Increase the motor on DRV-03 to 90 kW and re-size it." DRV-03 is currently variant ACS-R7-75-400 (frame R7), at item version 7. The steps below follow the request through every component of the architecture.

#ComponentWhat happens
1Browser → WAF → Integration APIThe question is sent with the Bearer token. The API verifies the token and builds the caller context: sales_engineer, country DE, customer group G1.
2Assistant containerThe orchestrator routes the question to the sizing agent. With the Private LLM, the agent prepares a preview call: preview_resize(DRV-03, 90 kW, 400 V). A preview only reads, so it needs no approval.
3Integration API: sizing read order① Redis size:{hash(inputs, apiVersion)}: miss. ② PostgreSQL sizing results for that input hash: miss. ③ Only now is the sizing adapter called.
4Sizing adapterChecks the circuit breaker (closed), takes a token from the sizing rate limit in Redis, and uses the cached OBO token for this user. A sizing run takes 1 to 6 s, so the call becomes an interactive job; its job ID is the input hash, so identical requests from other users merge into the same job.
5Worker (interactive) → Sizing toolThe worker calls the sizing tool over HTTPS REST. The response is validated against its schema: recommended variant ACS-R8-90-400 (frame R8), 88 % load. ④ The result is written to PostgreSQL and to Redis (fresh for 15 minutes).
6Human in the loopThe agent shows the proposal: R7 → R8, the BOM change and the price difference. The user clicks Confirm and the UI receives a signed confirmation valid for 5 minutes.
7Tool registry → Integration APIresize_item runs with the confirmation, the user's context and If-Match: 7. The sizing result is now a Redis hit, so the sizing tool is not called a second time.
8PostgreSQL (one transaction)The variant changed, so one transaction updates the item's variant and 3D model reference, its BOM line, sets version 8 and writes an outbox row. Either all of it is saved or none of it is.
9PricingThe entitlement check passes for a sales engineer. Price for R8 in DE/G1: Redis miss, then a valid PostgreSQL price snapshot, else the pricing adapter calls the ERP within its rate limit.
10Validator → SSE → BrowserThe answer is checked (prices allowed for this user) and streamed: "DRV-03 re-sized from R7 to R8 at 88 % load. BOM: R7 removed, R8 added. Price updated." An item.updated event makes the browser load the R8 model from Blob storage (lowest detail first) and refresh the BOM and price panels.
11Worker (interactive) → Host project APIThe worker claims the outbox row and saves the change to the host with If-Match and an idempotency key. The host's webhook for this change carries version 8, which is already applied, so it is ignored.
12Audit logThe question, the preview and resize tool calls, the confirmation and the answer are stored.

What changes in other cases:

  • Sizing tool down or circuit open: step 4 stops. The assistant says sizing is unavailable and nothing changes.
  • The user declines: step 7 never runs. No write, no outbox row.
  • Same variant recommended: step 8 writes nothing to the item or BOM; the answer says no re-size is needed.
  • Channel partner: the flow is the same, but step 9 returns not_permitted without calling pricing, and the validator ensures the answer contains no price.

2. Technology choices

The guiding rule is fewer moving parts. The real bottlenecks are the external systems' rate limits and outages, not our own compute, so every component must earn its place. The reference stack (Node.js, Express, MongoDB, Redis) was the starting point; we kept what fits and changed the database, with the reasons below.

2.2 Why PostgreSQL instead of MongoDB

MongoDB is the reference stack's database, so this choice needs the clearest reasoning. It comes from the shape of the data and the consistency the workspace needs.

NeedPostgreSQLMongoDB
Re-size must stay consistent. Variant, 3D model reference, BOM line, version and outbox row change together.One ACID transaction across several tables. All of it is saved or none of it is.Either embed the whole project in one document, which grows large and conflicts when several items are edited, or use multi-document transactions, which need a replica set and are not the usual Mongo pattern.
The data is relational. Project → item → variant → BOM line → price snapshot.Foreign keys and unique constraints (one BOM line per item) are enforced by the database.References between collections are checked only by application code.
Idempotency and concurrent edits.INSERT … ON CONFLICT for upserts by revision, unique idempotency keys, and a version column for optimistic locking (409 on mismatch).Possible with unique indexes and conditional updates, but each case must be hand-built.
Outbox to the host.The outbox row is written in the same transaction as the change, which is what makes the pattern reliable.Needs a multi-document transaction or change streams for the same guarantee.
Search over 12,000 variants.Built-in full-text search plus trigram indexes on variant codes. No separate search engine.Text indexes work; Atlas Search is a separate service outside the customer's tenant.
Variable product attributes.JSONB columns give document-style flexibility where it helps, while the core relations stay strict.Flexible documents are Mongo's strength.
Hosting in the customer's Azure tenant, with a security review.First-party managed service with private endpoint, Entra ID login, zone-redundant HA and point-in-time restore.Cosmos DB's Mongo API has compatibility gaps; Atlas runs outside the customer's subscription.
Scale (600 concurrent sessions, 5,000 users).A light load. Read replicas and connection pooling cover growth to 50,000 users.Also sufficient; scale does not decide this choice.

What we give up: the team already knows MongoDB, and its flexible documents would suit catalogue attributes and raw vendor payloads. JSONB covers that need without giving up transactions and constraints, which the re-size flow depends on.

2.3 PostgreSQL indexes

Indexes are chosen from the queries the service actually runs, not added to every column. Each one speeds up a hot read path or enforces a rule the data depends on. Three principles:

  • Index what the request path reads. The sidebar has a 1 s budget, so its lookups (item by ID, catalogue by variant, price by variant + country + group) must be single index lookups.
  • Let unique indexes enforce rules. One BOM line per item, one inbox entry per webhook event, one result per idempotency key. The database rejects a duplicate even if application code has a bug.
  • Keep write-heavy tables lean. Every index slows down inserts. The outbox and audit log get only what their readers need, using partial and BRIN indexes to stay small.

PostgreSQL creates an index for every primary key and unique constraint automatically, but not for foreign keys, so those are added explicitly where they are queried.

TableIndexTypeWhy (the query or rule it serves)
itemsitem_id (primary key)B-treeEvery sidebar, re-size and assistant call loads one item by ID. A single lookup of about a millisecond.

bom_linesproject_idB-treeForeign key. The project BOM endpoint reads all lines of a project.

sizing_results(input_hash, api_version) UNIQUEB-treeThe step ② sizing lookup. The same inputs on the same API version give the same result, so it is stored once and reused by every user.
catalogue_variantsvariant_code (primary key)B-treeThe catalogue panel reads one variant by code; items and BOM lines reference it.

Verified, not guessed: the hot queries are checked with EXPLAIN ANALYZE in tests against seeded data, and unused indexes are found with pg_stat_user_indexes and removed.

2.4 Other alternatives considered and rejected

AlternativeWhy not
Microservice per enterprise systemMore network hops inside a 1 s budget, cross-service coordination for global rate limits and a larger attack surface. Splitting would not raise the external limits. Adapters stay isolated, so any one can be extracted later.
Kafka or Azure Service BusRedis with BullMQ already covers priority, dedupe and retries with one fewer component. Service Bus is the upgrade path if stronger delivery guarantees are needed.
Elasticsearch or Azure AI Search12,000 variants fit comfortably in Postgres full-text and trigram search. Another cluster adds cost and operations.
WebSocketsPush is one-way; SSE is simpler and passes the WAF as plain HTTPS.
GraphQL gatewayAdds a schema layer, and partial failures are less explicit than a status per sidebar section.
API gateway product as the backendIt can route and throttle, but cannot hold the sidebar aggregation, per-section statuses or entitlement filtering. At most it sits in front as the edge.

3. Key sequences

All three sequences use the same project: a water-plant pump room with drive DRV-03, currently variant ACS-R7-75-400 (frame R7, 75 kW motor) at item version 7. Every data read follows the same order: ① Redis, ② PostgreSQL, ③ adapter to the external system only on a miss, ④ write the result back.

3.1 Sequence 1: the engineer clicks a drive and the sidebar fills (sizing tool down)

Goal: useful content in every panel within 1 s, even though the sizing tool is down.

Result: one failing system turns one panel stale; the other panels are unaffected and the response stays inside the 1 s budget. During the nightly sizing maintenance window the breaker is opened in advance, so users see the same behaviour without waiting for failures.

4. Assumptions

  1. Identity: Microsoft Entra ID is the identity provider. It authenticates users and issues the claims used for authorisation (role, country and customer group). The Integration API makes every authorisation decision from those claims, on the server.
  2. Rate limits: the vendors' rate limits (sizing 20 requests per second, pricing 5 requests per second) apply to our whole service, not to each user. All API replicas and workers therefore share one set of counters in Redis.
  3. Cache lifetimes: a sizing result depends only on its inputs and the sizing API version, so it is cached and reused for 7 days. A price is cached for as long as its quote is valid (24 hours) and is never served after the quote expires.
  4. Stale data: when an external system is down or unreachable, users prefer to see the last known data, clearly marked as stale with its age, rather than an empty panel.
  5. Re-sizing: a re-size updates the existing item's variant and its stored sizing result. The item keeps its identity (item_id); it is never replaced by a new item.
